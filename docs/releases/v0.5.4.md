# Crafleet 0.5.4

Crafleet 0.5.4 adds explicit live file operations and settings deployment, configurable operational limits, and fixes for workspace inspection and legacy YAML migration.

## Operate on running servers

Use `--force` with `files track`, `files capture`, `files resolve`, or `files migrate --from config` to operate while a server is running. `files untrack` now works without stopping the server or changing runtime files. Read-only inspections, previews, and pending preparation remain available without force.

Live reads cannot capture unsaved in-memory data or guarantee consistency across files. Detected changes still abort the operation. Migration changes management directories and metadata without rewriting runtime; update and restart management tools when needed.

`deploy apply --force` can deploy changes to YAML, JSON, TOML and properties files while running when an active deployment exists and JARs and launch conditions are unchanged. Additions and deletions follow the same restriction. A pending installation containing any unsupported runtime change is rejected as a whole. Recovery groups validate every member before writing.

Live deployment saves protected copies of affected settings under `.crafleet/live-deploy/` instead of creating a normal backup. These copies do not cover worlds or databases. Interrupted recovery requires shutdown and restores only the affected files. Crafleet does not automatically stop or reload the server.

Writing files does not confirm that the server has applied them. Plan a restart for Paper, or use a reload only when the affected component supports it. The server may overwrite the files during its own saves. Text-based plugin save data can also qualify by extension, so review the pending changes before applying them. See the [versioned operations guide](https://github.com/sya-ri/crafleet/blob/v0.5.4/docs/operations.md#running-settings-deployment).

Warnings appear on stderr before changes. JSON success and error envelopes may now include an optional `warnings` array; existing `result` shapes are preserved. These force options do not bypass starting, stopping or unknown process states. JAR/binary deployment, normal backups, restoration and recovery still require shutdown.

## Configure operational limits

Set limits in project/workspace `settings`, through `CRAFLEET_SETTINGS_*`, or with repeatable `--set key=integer`. `settings list` shows the catalog; `settings show` shows effective values and sources. Defaults preserve existing behavior, and supported limits accept integer `-1` for unlimited operation. See the [versioned settings reference](https://github.com/sya-ri/crafleet/blob/v0.5.4/docs/settings.md) for keys and precedence.

`java.startupTimeout`, `java.stopTimeout` and `PI_TUI_ESC_TIMEOUT` remain accepted with deprecation warnings. Replace them with `settings.runtime.startupTimeoutMs`, `settings.runtime.stopTimeoutMs` and `CRAFLEET_SETTINGS_CONSOLE_ESCAPE_TIMEOUT_MS`. Convert the old Java timeout values from seconds to milliseconds. No removal version is scheduled for these aliases.

## Fixes and upgrade

Workspace inspection results are grouped by project, including empty results. Legacy configuration migration preserves YAML sequences and mappings.

Install with `npm install --global crafleet@0.5.4`. Node.js 24, 25 and 26 remain supported. Updating the CLI does not update running runners, supervisors or console addons: update the addons and restart managed processes before relying on changed runtime limits or new live-operation behavior. Legacy `config` tracking, capture and resolution now require `--force` while running, matching `files`.

No automatic project migration is required. Legacy `config/` projects remain supported through 0.5.x; their removal in 0.6.0 is separate from the timeout-alias deprecations.
